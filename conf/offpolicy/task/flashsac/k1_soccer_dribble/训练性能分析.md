# K1 带球 vs 平地走 · 训练墙钟性能分析

> 对比对象：FlashSAC owner、`num_envs=1024`、Motrix（带球必选）/ MuJoCo（平地可选）。  
> 与 [`任务分析.md`](任务分析.md) 的功能说明互补；本文只讨论 **相同 control step 数下为何更慢**。

---

## 1. 结论摘要

在 **相同 `max_iterations`（每个并行 env 每 iteration 前进 1 个 control step）** 下，带球训练墙钟明显长于平地走，主因是 **每个 control step 的物理子步更多**，其次才是 **场景接触更复杂** 与 **Python 侧 reward 更重**。

| 对比 | 约慢多少（仅 `env.step`） |
|------|---------------------------|
| K1SoccerDribble **motrix** vs K1WalkFlat **motrix** | **~3.3×** |
| K1SoccerDribble **motrix** vs K1WalkFlat **mujoco** | **~4.7×** |

「约 2×」若来自混用后端（平地 mujoco、带球 motrix）或 iteration 里采集/learner 占比不同，会低于纯 motrix 对比的 ~3.3×；以本机复现脚本为准。

**观测历史帧（5 帧堆叠）已移除**，不是当前变慢主因。

---

## 2. 复现方式

仓库脚本（与训练相同的 Hydra compose + `BackendAdapter` 注入 `reward_config`）：

```bash
uv run python scripts/benchmark_k1_walk_vs_soccer.py
```

默认：`num_envs=1024`，warmup 20 step，计时 200 个 **control step**（`ctrl_dt=0.02 s`）。

## 3. 实测数据（本机 Motrix / MuJoCo，2026-06）

| 任务 | 后端 | `sim_dt` | `sim_substeps`¹ | 秒 / control step | 并行 env step / s | 激活 reward 项² | `updates_per_step`³ |
|------|------|----------|-----------------|-------------------|-------------------|-----------------|---------------------|
| K1WalkFlat | motrix | 0.005 | **4** | 0.033 | ~31k | 21 | 2 |
| K1WalkFlat | mujoco | 0.005 | **4** | 0.024 | ~44k | 21 | 8⁴ |
| K1SoccerDribble | motrix | 0.002 | **10** | 0.110 | ~9.3k | 29 | 1 |

¹ `sim_substeps = round(ctrl_dt / sim_dt)`，见 `src/unilab/base/base.py`。  
² `len(reward_config.scales)`，非零 scale 的项数。  
³ FlashSAC owner；learner 更新次数 **不能**解释带球更慢（带球反而更少）。  
⁴ `conf/offpolicy/task/flashsac/k1_walk_flat/mujoco.yaml` 默认 4096 env；benchmark 脚本统一 override 为 1024。

**比值（motrix 对 motrix）**

- 墙钟：`0.110 / 0.033 ≈ 3.35×`
- 子步数理论：`10 / 4 = 2.50×`
- 剩余约 `3.35 / 2.50 ≈ 1.34×` → 归因于场景/接触与 Python reward 等

## 4. 原因分解（按贡献）

### 4.1 物理子步数（主因）

| 任务 | `ctrl_dt` | `sim_dt` | 每 control step 子步 |
|------|-----------|----------|----------------------|
| K1WalkFlat | 0.02 | **0.005** | **4** |
| K1SoccerDribble | 0.02 | **0.002** | **10** |

`NpEnv.step` 每次调用 `backend.step(ctrl, sim_substeps)`（`src/unilab/base/np_env.py`）。

带球 `sim_dt=0.002` 写在 `K1SoccerDribbleCfg`：Motrix 下 **box 地面 + 足球 mesh** 接触在 `0.005` 易发散，需更小步长（见 `soccer_dribble.py` 注释与 `scene_soccer_dribble_minimal.xml` / `zzz_debug/BALL_PHYSICS.md`）。

### 4.2 场景与接触（次因，约 ×1.3）

| | 平地走 `scene_flat.xml` | 带球 `scene_soccer_dribble_minimal.xml` |
|--|-------------------------|----------------------------------------|
| 地面 | `plane` floor | `COL_Collider` box |
| 额外动力学 | 无 | 足球 **free joint** + **mesh** geom |
| 足地 contact 传感器 | `geom1=floor` × 8 | `geom1=COL_Collider` × 8 |

同样子步数下，每步求解的接触对更多，mesh-box 一般比 plane 贵。

### 4.3 Python：reward / 状态（次要）

带球继承 `K1WalkEnv` 行走项，并增加约 **8 个 `ball_*`** 等项（owner 共约 **29** vs 平地 **21**）。多项 reward 各自调用 `_ball_state()`（base pose/vel + `get_body_pos_w` / `get_body_lin_vel_w` + 机体系变换）。`update_state` 另有朝球命令、丢球终止、`feet_step_travel` 等。

相对 Motrix 物理耗时，占比通常较小，但在高 `num_envs` 时会叠加。

### 4.4 训练配置（不导致带球更快）

| 项 | K1WalkFlat motrix owner | K1SoccerDribble motrix owner |
|----|-------------------------|------------------------------|
| `updates_per_step` | **2** | **1** |
| `warm_start` | 无 | K1WalkFlat ckpt（**仅启动一次**） |
| `curriculum` | 开 | 关 |

整轮 iteration = 采集 + learner 时，walk 每步还多 1 次 GPU update，会 **部分抵消** 仿真变慢，但仿真差 ~3× 时总墙钟仍偏慢。

### 4.5 与「相同步数」的关系

FlashSAC 默认 `env_steps_per_sync: 1`：  
**1 iteration ≈ 每个并行 env 1 个 control step**。  
故 `max_iterations` 相同 ⇒ **环境交互步数相同**；墙钟差主要来自 **每步成本**，不是多采了步。

## 5. 优化方向（需单独验证）

| 方向 | 预期收益 | 风险 |
|------|----------|------|
| 带球场景验证后尝试 `sim_dt=0.005`（子步 4，与 walk 对齐） | 最大（约 ÷2.5 物理量） | 接触发散，需物理回归 |
| 每 control step **只算一次** `_ball_state`，供所有 ball reward 复用 | 小到中 | 实现成本 |
| 对比时 **统一后端**（平地也用 motrix） | 避免 mujoco vs motrix 混比 | 无 |
| 再减 `updates_per_step` | 有限 | 样本效率下降 |

**不建议** 为提速恢复 5 帧 obs 堆叠；已与推进式单帧策略相反。
